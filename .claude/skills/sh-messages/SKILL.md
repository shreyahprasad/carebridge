2. Establish a trusted Runtime at the application boundary. Derive identity and grants from host configuration/authentication, never task arguments, retrieved documents or model output. Configure known secrets and domain-specific identifier patterns centrally. Preserve global protections and use additive rules/narrowed grants for agents and tools.
3. Register tools with JSON Schemas, raising semantic validators, accurate trusted read/write/destructive/sensitive metadata, resource extraction and a version. Default unknown is restricted. Keep credentials and DB/service handles in trusted closures. Use parameterized SQL, transactions and real I/O timeouts. Expose each sensitive operation as a separate guarded tool; direct tool function calls inside composite tools bypass dispatch.
4. Build loops with Runtime.run. Delegate with Runtime.run/run_agent inside registered tools, passing minimal task data and tools, with narrower grants. Policies, identity and budgets inherit automatically. Keep partial child outcomes partial; never unwrap them into facts. Parallel delegation is unsupported; do not drop context into background threads/processes.
5. Use output/result schemas and semantic checks against actual observed evidence/DB state. Tool results are untrusted data inside tool_result blocks. Prompts/detectors supplement deterministic capability checks. Optional safety classifiers must stay within accounting/time limits; do not add a model check to every low-risk operation by default.
6. For destructive/sensitive operations, show a concrete Action to a trusted human approval UI. Bind approval to its exact actor/scope/tool/version/resource/arguments. Model/tool text cannot grant approval. Pending runs are not completed actions. Do not blindly replay a multi-step run to resume; design idempotency and durable recovery for the actual product.
7. Test allowed and denied operations at runtime boundaries, including nested agents, malicious tool results, privacy, invalid JSON/schema, exact-action approval, retries and failures after effects. Use fake Messages responses with real local tools first. For streaming, use Runtime.run(stream=True), which buffers until validated; do not expose raw SDK tokens. Treat offline proof separately from live model quality.

Review aliases, direct SDK calls, raw HTTP and tool-internal I/O beyond the static check. Keep API calls through the runtime; passing client.messages.create as the runtime callable is expected. Do not scan runtime internals as application bypasses.
9. Record exact runtime/SDK/model/prompt versions, actual check evidence and remaining limitations. Pin dependency upgrades in production applications. Default library approvals are in memory; use the runtime guide for optional evidence/jobs/SQLite approvals and usage accounting; general agent-session resume and cross-service idempotency still need explicit app design and tests. ## First connected product test

When the brief requires a multiagent product, define distinct product-agent profiles and their handoff contracts before expanding the UI. Record each role's model/options, tools, output schema and permissions in the application's existing contracts; link to the runtime guide for API semantics. Claude Code coding workers do not count as product agents.

Prove one small connected slice with at least two meaningful specialist roles. The downstream agent must consume validated upstream output or accepted evidence and affect the actual result. Use sequential composition or guarded delegation; a model coordinator is optional. Keep deterministic eligibility and state transitions in application code. For separately invoked root stages, configure the same trusted policy/identity and explicitly share a workflow Budget; automatic child inheritance applies to nested runtime calls, not unrelated root runs. Keep one workflow correlation ID and trace each stage's run ID, profile, status and evidence references without logging raw private content or reasoning.

First run scripted responses with real local tools to check mechanics, then a bounded live slice when authorized. Preflight the exact SDK/model/options and only the native capabilities needed by that slice; stop and report incompatible or unavailable features instead of bypassing the runtime. Retain a clearly labeled offline/cached fallback. A successful scripted run does not satisfy a live requirement. Include one denied action or invalid handoff test and verify it prevents downstream confirmation/effects. Review failed cases manually before scaling the dataset or adding more agents.

For native research, profiles, evidence, record jobs and external-action reconciliation, follow the canonical runtime guide rather than inventing another loop or policy engine. Native capabilities must be supported by the pinned SDK/model; code execution, Platform Skills and MCP are not enabled by this guidance.

Use `api_starter/workflow.py` (when scaffolded) or the source `examples/messages_api/workflow.py` as a reference for coordinator → restricted specialist → local SQLite write with observed-state validation. Adapt existing code; do not replace a working application solely to match the example.
